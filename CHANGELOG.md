# Changelog

Code changes by milestone. Specification changes are in [docs/SPEC.md §14](docs/SPEC.md#14-change-log).

## Unreleased

### Engine (E0.19 measure honestly, and fewer reviews)
- **Review KPIs at run time (step 1).** `npm run engine:kpi` measures a run (a batch file, a job, or a project's last run) against one frozen baseline (`test/baseline/kpi-baseline.json`): cases set aside, questions (one per review card), reviews per 100 written steps, flaky rate, wrong PASS and wrong FAIL against an answer key, active review time and walkthroughs. Opening a review is noted once a minute (`review.view`), so review time is measured.
- **One card per real question (step 2).** A card is the sentence the engine could not decide and why; cases that ask the same are one card, and the headline is that sentence (it was the first check that had not run, e.g. "Verify User should open browser"). Add Employee: 7 cards → 3.
- **Ask once per project (step 3).** The new engine now reads the project's readings (it read the test case as written, so an answer never reached it). A wording card takes an answer, "It means …", kept for every case of the project with that sentence.
- **One-click rewrite (step 4).** A wording card offers up to three sentences that run, built from names the screens showed and read by the engine first; else the engine's pattern to fill in.
- **A wrong PASS closed (step 5).** On saved OrangeHRM pages broken on purpose, "The "Login" button is displayed" passed on the label "Login Name :" with no Login button. A named button, link, field, dropdown, checkbox or radio button is judged only by elements of that kind with that name; a real button whose words are its value is now found too. Six faults on four saved pages, none survives.
- **The gate in CI (step 6).** `engine:gate` reads saved live runs (`test/baseline/runs`): a wrong PASS against the answer key blocks; the 80% minimum of fewer questions blocks once the owner declares the minimum engine in `gate.json`.
- **Holding area for flaky cases (step 7).** A flaky case can be held by an owner, with a reason, for 1 to 30 days (migration 10 `held_cases`); it still runs, stays listed, is not a question while held, and comes back by itself, overdue, when its day passes.
- **Measured live (step 8):** questions 19 → 6 against the legacy engine (−68%; Add Employee 13 → 3, Login 6 → 3); wrong PASS 0 against the draft answer key. Not yet the 80% minimum; the remaining questions are the owner's (see `docs/ENGINE-PLAN.md` §E0.19).

### Engine (E0.18 honest verdicts and review memory)
- **STATE checks the new engine judges (step 1).** "PIM is the default page" is judged on the page the login left: proven when one of that menu's own links opens the screen shown (OrangeHRM 2.5: PIM's Employee List), or when the address names the page; disproven when another menu's link opens it. "Upload button should accept photo" is judged on the file field. "User should updated the data" stays a person's (gold, 4 Nov 2026). Observations keep the page's menus with the addresses they open. An upload step that names its control only by what it does ("the upload button") uses the page's one usable file field.
- **One case on its own runs through the new engine (step 2).** Approve and the re-run of a saved case now run a case the old parser does not read and the new engine does (`runnableOf`); before, Approve said "Nothing to run yet". The message is honest: "Runs through the new engine", or why it cannot yet (no more "until the switch-over").
- **The shadow gap is closed (step 3).** A legacy PASS the new engine cannot run itself (a check kind it does not judge, an unread case, a case that starts logged in with no login case) is NEEDS REVIEW with the reason (owner, 7 Nov 2026). A PASS after a person picked an element on the screenshot stands (owner, 7 Nov 2026). Each case the new engine runs may take 5 minutes at most (`AUTO_QA_CASE_TIMEOUT_MS`); one that runs over keeps its review and the batch goes on. "Open the Login page" with no address known opens the application's own address and says so.
- **Every NEEDS REVIEW says why (step 4).** One label of eight (`src/results/labels.ts`): inconclusive, healed, chosen, flaky, not-found, hidden, ambiguous, wording. The five statuses stay (owner, 7 Nov 2026). Shown in the terminal report and its summary, the new `Review Reason` column of the results workbook, and the job page. The generated config retries a failed test once (`AUTO_QA_RETRIES`, 0 to switch off); the reporter keeps one record per test and a pass on the retry is NEEDS REVIEW, flaky.
- **Approval fingerprints (step 5).** A check left open records a fingerprint: its sentence, condition and expected value, the step's action and element, and what the page showed (`approvalFingerprint`). Each run reads the project's current review decisions with those fingerprints (`Store.decidedChecks`) and judges an unchanged decided check by that decision; another expected value, element or page asks again. Changing a PASS to FAIL makes the next run read FAIL and switches off the elements that PASS kept for their screens. Before, no run read the review decisions back.
- **Learned entries with a worked example and a conflict check (step 6).** A reading keeps what the engine read its new sentence as when it was saved (`readsAs`); a run sets it aside when the engine reads it otherwise now. A reading that chains with or undoes an active one, and a label that chains or cycles with one in the same place, is refused with the reason (`src/learning/conflicts.ts`).
- **The review card (step 7).** The card shows the reason label and its meaning, and says that the decision is remembered for the next run of the same checks. The project export has `Review Reason` and `Decision` (who, when, why) beside the engine's status, which a decision never changes, and counts decided cases.
- **A wrong PASS closed (found in the step 8 live run, owner decision 7 Nov 2026).** BookMarket TC01 "User should navigate to Book Market Home Page" passed on the login page: the first run had saved "Book Market Home = /login" from that same page (D19, silent), so the check proved itself. The explorer no longer names a page from the check that is judged on it: when the address does not name the page it asks "Is this the … page?", and learns it only when a person says yes (`ExplorationResult.confirmedPages`, page route source `tester`; the command line keeps `pages.confirmed.json` beside `pages.json`). An address that names the page ("/dashboard" for "Dashboard") is evidence and is used as before. The verdict engine uses only confirmed addresses to prove or disprove a URL check (`unconfirmedPages`); addresses saved in silence still open pages. On BookMarket, TC01 and TC05 are now NEEDS REVIEW.
- **Measured** (`npm run engine:review -- --no-examples`): ready cases 10 → 22, cases waiting for engine work 12 → 0, review reasons 26 → 14 (all a tester's); gold unchanged (771 of 796); traps 10 of 10. Live (local OrangeHRM 2.5, BookMarket online): Add Employee 19 cases, 4 FAIL, 15 NEEDS REVIEW, each review one the owner's decisions call for (9 the login-box layout, one card; 5 "which employee"; 1 wording); the 4 FAIL read "empty text boxes after Reset" as the gold reads it, while OrangeHRM puts its auto-numbered Code back (0002). OrangeHRM login workbook: its Test Data is for the account cypress, which this install does not have (1 FAIL, 4 BLOCKED by the S4 guard).
- **Not done:** a decision on a NEEDS REVIEW of the old engine has no fingerprint and is not reused (it closes when the old engine is retired, E1.0). Retries run a failing test twice, so a test that saved a record before failing saves it again; the old route writes no clean-up list. A case with no upload step reads "Upload button should accept photo" as another kind of check (NEEDS REVIEW, never PASS). A hang of 10 minutes seen once in a new-engine upload case could not be reproduced; the per-case time limit now stops such a case. Found, not fixed: a value written in a step after "Note:" ("Enter the given valid Email … Note: student@bookmarket.com") is not used, and a valid value is made up instead (BookMarket TC05).

### Engine (E0.17 locating like a person)
- **Nested containers (item 2).** "The login section" is the part of the page that holds the login words and at least two controls; of holders inside each other the innermost is meant, and a part with fields is the box around its fields and buttons (`src/engine/locate/holders.ts`). Observations keep these parts and the window size, and the new engine judges LAYOUT checks. Owner, 6 Nov 2026: the innermost box and the parts of the same words around it are all measured; when they disagree (OrangeHRM 2.5: the box is left of the middle, its panel is in it) the case is NEEDS REVIEW with each measurement.
- **Container anchors (item 1).** Steps keep the section, panel, box or tab they name ("Click Edit in the Job section", "Enter Rao in Last Name in the Personal Details section"); they were dropped. On a page that marks no sections, the part whose title is the name is the anchor and only what is inside it is searched; two parts with the title are a question; none: a card must still be found, a section is read on the whole page and the run says so (`src/engine/locate/anchors.ts`).
- **Off the page is hidden.** An element left of or above the start of the page is hidden ("off the page"): OrangeHRM 2.5 parks closed tabs and hover menus at x -9999, which made 4 Edit buttons and 2 Job links look equal.
- **Identical elements (item 3).** Candidates alike in role, name, handler (now read: `onclick`, `href`), form, frame, kind, test id and name attribute are one control shown more than once. To act, the one in the part of the page the case is working in is used (nearest to the step before, owner decision), else the first on the page, as an assumption: NEEDS REVIEW, never PASS, and a failed check after it is NEEDS REVIEW too, not FAIL. To check, they stay a question; inside named containers too. A PASS on the review card keeps the choice as a screen label (`TestVerdict.picks` → `LearningService.saveLabel`), so the next run uses that element without asking.
- **Row actions (item 4).** "Check the checkbox in the row for Anita Kumari Rao": a control the step names only by its kind is the only one of that kind in the row (`LocateQuery.onlyOfKind`). A name kept in columns next to each other matches when its words run across them in order (`src/engine/execute/row-match.ts`). "Tick the box" is a checkbox. Checks read their row as steps do, observations keep each control's row, and the new engine judges checked and unchecked boxes.
- **Fallback fingerprints (item 5).** What a step found is kept with its screen as a fingerprint: its unique locators in LC-01 order and weighted features (`src/engine/locate/fingerprint.ts`, `Screen.found`). When a later run finds nothing by any level, to act, exactly one usable element of the same role and frame scoring at least 0.6 and 0.15 ahead of the next is used, as an assumption (NEEDS REVIEW). Never for a check, never in a named row.
- **From E0.14.** A `<label for="x">` that has the id "x" too still names its field (OrangeHRM 2.5 First Name); a link of a hover menu is reached by hovering the item it hangs from, once.
- **Also:** a label may name the same action it is for when it is a pick on one screen ("Edit" is that Edit button). Demo app pages `/ui/alike`, `/ui/rows`, `/ui/renamed`, `/ui/menu`; OrangeHRM 2.5 fixtures `test/dom/orangehrm-{login,employee,employee-list,add-employee}.html`.
- **Measured** (`npm run engine:review -- --no-examples`): review reasons 27 → 26, ready cases 9 → 10; gold unchanged (771 of 796); traps 10 of 10. Live on local OrangeHRM 2.5: Job section Edit, plain Edit on the Job tab, the row checkbox of Anita Kumari Rao and Add Employee from the PIM menu PASS; TC01 is NEEDS REVIEW as decided.
- **Not done:** 12 cases now wait for STATE checks the verdict engine does not judge (DEFAULT_PAGE, UPLOADED, UPDATED; they were hidden behind LAYOUT), for E0.18. A screen label kept by a PASS is not taken back when the decision is changed to FAIL (E0.18 approval fingerprints). "Check the Remember me box" is still read as a check.

### Engine (E0.16 setup blocks, data ledger, test data)
- **Setup blocks (item 1).** The leading lines most cases of a sheet share (open the browser, open the application, check the login page, check the tabs) are found once per sheet (`src/engine/context/setup.ts`). A block only ever holds lines that are setup by kind, so a data-entry line many cases share is never taken for setup, and a line that takes its value from the Test Data is not setup either (TC_LOGIN_003 keeps its wrong password). Nothing is removed from a case: each still runs and checks all it says.
  - A question about a setup line is the sheet's: the review report counts it once (`Issue.block`). A setup line that cannot be read and only restates the line before it ("Verify User should add button…" after "there should be add button") is set aside with the reason, and the check before it still runs. On Add Employee the question raised in 16 cases is raised in none; TC03, which tests that line, still asks.
  - **The login the cases assume (E7).** When the setup checks the tabs right after the login page and no line logs in, the case logs in there with the project's login (`TEST_USERNAME`, `TEST_PASSWORD`), with the fields and button of the project's login case when there is one; the login page is still checked before it, the tabs after it.
  - Batch runs read the block from the whole sheet, also when only the review queue runs; `engine:review` and `engine:lint` read it too. `engine:gold` reads each case on its own, so the signed gold readings do not change (771 of 796, as before).
- **Data ledger (item 2, U5).** Every value a case enters is written down with its step, and each Save makes a record: the kind of thing ("Employee", from "Add Employee"), created or updated, the page, and a Reset before the Save if there was one (`src/engine/context/ledger.ts`). References are read through it: "the entered details" are everything entered on the page (not only the last field); "the added employee (in the list)" and "the updated record" check the values the case saved; "the previous page" is the page before the current one (it was read as a page called "previous"), and is asked about when there is none.
  - **Which record stays a person's decision** (owner, 4 Nov 2026): "Click on Employee Name", "the same updated records", "Select preferred Employee", "Deleted Employee Data" are still questions, and now carry the record this case saved as the suggested answer (`Issue.suggested`). The review report asks each such sentence once for all the cases that have it, as the tester's.
- **Test Data per step (item 3, P2).** A row with only an expected result or only test data belongs to the step above it, instead of starting a broken case or being skipped as a heading. Each row's own data is kept by step (`RawTestCase.stepData`) and read by that step first, so two steps can give the same key different values (a wrong, then the right password), each with its own data key and secret.
- **Unique names and a clean-up list (item 4, P3).** Made-up values are seeded by the run (`runSeed`), so each run creates records with names of their own (before, every run typed the same names). Each run of the new engine writes `cleanup.json` and `cleanup.txt` into its run folder: every record whose Save the run reached, with the values it was saved with (secrets `***`). Nothing is deleted (PD-15).
- **Workers (item 5, P5).** The generated Playwright config sets workers: one by default (it set none, so files ran side by side as the same user), more with `AUTO_QA_WORKERS`, never more than the accounts given (`TEST_USERNAME_n` / `TEST_PASSWORD_n`); worker n logs in as account n; every test starts with no saved login. Tested with real runs on the demo app (`src/generator/workers.test.ts`).
- **Fix:** step 1 had left mis-encoded characters in `case.ts`, among them the curly quotes used to mask a secret typed in a step; they are restored.
- **Measured** (`npm run engine:review`, both OrangeHRM workbooks): 37 review reasons before E0.16, 32 after item 1, 27 now; gold unchanged (771 of 796).
- **Not done:** reusing a worker's saved login across its tests (the generated tests log in themselves, so a saved login would clash with their login steps); the legacy route writes no clean-up list (only the new engine's runs do); importing more than one sheet (also P2).
- **Decisions (5 Nov 2026, PD-15):** clean-up lists what a run created and deletes nothing by itself in V1; runs stay at one worker until more test accounts exist.

### Engine (E0.14c record in the walkthrough, PD-14)
- **A valid email address is the project's login.** "Enter the valid Email address" was read by the new engine as "make up a valid email", so a walkthrough typed `qa.…@example.test` and the login failed. A valid email, email address, email id, user id or login id is now `TEST_USERNAME`, as the old parser already read it; a bare "Email" still needs a value.
- **The walkthrough's browser is a window you use.** While the walkthrough waits, what is done in it is recorded as steps of the case, on every page reached: clicks, typing, dropdowns, checkboxes, radios, Enter, Escape, and addresses opened by hand. Each step is kept only when both the new engine and the old parser read it back as that action on that element; the login is written as the valid username and password, never the password itself (`src/server/recorder.ts`).
- **"I did this step myself"** on a step that cannot find its element: the recorded actions take its place, and its words are remembered as the element used on that screen.
- Recorded steps can be removed before saving; they are saved with the checks, as a new version, only on a yes. `AUTO_QA_WALKTHROUGH_HEADLESS=1` hides the window.
- **The owner's first use on BookMarket (3 Nov), fixed:**
  - **One window, with the steps in it.** The browser opened a second, empty window; it is closed now. The window has a panel on the left: the steps (done, here), what was recorded, and the buttons for what the walkthrough waits on (Next step, Finish, I did this step myself, Yes or No, save). The page is moved right while the panel shows and the panel is hidden while the engine runs a step, so it covers nothing and is in no screenshot; it is in a closed shadow root, so neither the engine nor the recorder takes its buttons for the application's (`src/server/walk-panel.ts`).
  - **A recorded action is a step only once the person adds it.** Each one waits for Add or Remove, in the window and on the Auto QA page (Add all for several); one not added is not saved, and "I did this step myself" is the OK for what was done for that step. Any change can be removed at any time while the walkthrough is open (`POST /api/jobs/:id/walkthrough/pending`). Before, a field typed again by hand after the engine had typed it was saved as a second step.
  - **Closing the window ends the walkthrough, and loses nothing.** It used to fail the job and drop what was recorded. Now the save question comes on the Auto QA page.
  - **Finish** ends a walkthrough before its last step. When saving, recorded steps can replace the steps that were not run, so a flow done by hand is not followed by the old steps again.
- **A run no longer fails on a long step on Windows.** Each step's screenshot was attached as a file, which Playwright copies under a name made from the whole step text; with several steps run as one block the path passed 260 characters (`ENOENT … copyfile`). The screenshot now stays where it was taken and the reporter is told its path in a note.
- **Walkthrough on every test case:** the project's test case list has a Walkthrough button on each row, not only on review cards; it logs in first with the workbook's login case when the case's last run had one.
- Not done: double click and hover; emptying a field; values with a double quote.

### Engine (E0.14 learn the application: run capture and the guided walkthrough, PD-13)
- **No scan and no crawl.** The engine learns each screen from the runs it already makes: every observation now keeps label, placeholder, input type, ids, frame path and the element's box on the screenshot (frame offsets added), the headings, table headers and an open dialog, and a **screen key** (the content frame's address with the parameters that choose the screen, plus the dialog). The screens a new-engine run reached are saved per case (`screens.json`) and come back as `Application.screens` in the next compile; a changed label is reported as one rename, because elements keep an identity that does not depend on their label (`src/engine/knowledge/screens.ts`, `src/engine/execute/capture.ts`).
- **Step-through hook** in the new engine's runner: asked before and after every step, can stop the run (`STOPPED`, judged NOT_VERIFIED), and a step that finds no element or several asks for a pick on the screenshot instead of stopping. Without a hook a run is exactly as before.
- **Guided walkthrough** (`Walkthrough` on each case of a review card, a `walkthrough` job): steps on the left, the screen after each step on the right; Next, Add check, Edit step, Stop. Seven check types (visible, not visible, text contains, value, enabled, disabled, URL contains), each written as a sentence and kept only when the engine reads it back as exactly that check, tried on the screen first. Before a step that saves, submits or deletes the person is asked; on a production environment such a step is refused unless the project allows it. Changes are saved as a new version (reason "edited in a walkthrough…", so it wins when the workbook runs again) only on a yes. A pick can be remembered for that screen only, by the element picked. A walkthrough left without an answer for 15 minutes is closed. A card says when its test case changed since the run.
- Not done: a live video of the browser; applying a check to similar cases; the legacy route.

### Engine (E0.13 frame-aware execution, new engine only)
- A screen two frames deep is read and acted on: frame paths of any length, a read that is made again once when the page changed under it (`readSettled`, `isNavigationRace`), and a frame that still cannot be read is listed (`unreadFrames`) instead of being taken as empty.
- While a frame is unread, a check that is disproven or "not shown" only because something was not found is unproven with doubt NOT_OBSERVABLE, never FAIL or PASS; what was found stays found.
- The screen is the content frame (the largest visible frame, then the frame inside it that still takes a quarter of its room): "redirected to the Dashboard page" and "stays on the page" look at the address of the frame as well as of the shell, and record ids and page numbers in an address are not a different screen (`pageIdentityOf`).
- Not done: the legacy parser/explorer route, and the rewritten OrangeHRM workbook for TC12 to TC19 (not in the repository).

### Engine (E0.12 safety, and the packages that closed the gaps of E0.0 to E0.11)
- **A valid login from the sheet no longer fails.** The parser's masked copy of the Test Data (`Password: ••••`, kept for storage and display) was what the new engine was given, so it typed four bullet characters as the password. The engine now reads the text the tester wrote, kept in memory beside the model (`parser/original.ts`), and a value made only of mask characters is never typed, in the resolver or the executor. Found on the real OrangeHRM; the tests now go through the product's own path (`src/pipeline/engine-input.test.ts`).
- **"Leave the field blank" works.** The executor empties the field and checks it is empty; an empty value that is not a blank is still refused.
- **A native alert is a message.** OrangeHRM answers a blank field with `alert "User Name not given!"`, which the page does not show; the judge now treats what a pop-up said as a fresh message, so a different wording is set aside for a person instead of failing the case.
- **A page name the engine cannot place is not a FAIL.** "OrangeHRM home/dashboard" means either page, each side is looked up among the known addresses, and an address is called wrong only when the engine knows where the named page is, or knows the page it is on is another one.
- **Safety:** the iframe "not displayed" trap (never a PASS for what a frame shows); a deleted project with learned entries no longer fails on a foreign key.
- **E0.9 login with a code:** TOTP (RFC 6238 vectors), an email adapter with a local test mailbox, a code only from mail received after the login step, replay protection, ENVIRONMENT_ERROR when no mail comes and TEST_DATA_ERROR when a code is refused, never FAIL (`src/engine/auth/`). No real mail provider yet (PD-5).
- **E0.10:** the audit trail of every call tied to its step and locator contract (`src/engine/audit/`); caching of what is worked out from text, with the same results on and off and no page evidence ever cached (`src/engine/cache/`, `npm run engine:cache-bench`); learned entries replace the project rules as the only thing a run reads (migration 0008, `npm run rules`), with a reading that turns a sentence into a "not shown" check refused, and four live rules that judged nothing quarantined.
- **E0.8 review card:** a person's PASS or FAIL on a case the engine could not decide, stored with who and when beside the engine's verdict, which it never changes (migration 0009, `/api/jobs/:id/review-queue`).
- **E0.7 cards and lists (UI-07):** a step or a check about "the Backpack card" keeps the card, and is done and judged on that card only; twins and a missing card are never guessed. Quoted text is matched as whole words ("$9.99" is not in "$29.99").
- **Case styles** (`userName`, `user_name`, `user-name`) and tests for the sheet column names (IN-06, IN-07, IN-11, IN-13).
- Verification of E0.0 to E0.11 against the plan's exit tests: [docs/VERIFICATION-E0.0-E0.11.md](docs/VERIFICATION-E0.0-E0.11.md).

### Fixed
- **Elements inside iframes** (OrangeHRM shows its whole content in one). The element the tester picked was never accepted, because page locators do not look inside a frame: every locator "matched nothing" and the same question came back. Locators now carry the frame they are in (`frameLocator('iframe[name="rightMenu"]').getByRole(…)`, nested frames too), the generated Page Objects use them, and Playwright MCP's `locator(…).contentFrame()` code is read. The picture of the page also drew frame elements in the wrong place (a button 100px down the page showed at the top): their boxes are now moved by the frame's offset. `src/locators/frames.test.ts`.
- "Open the application" / "Enter the URL" opened the site root instead of BASE_URL with its path.
- A redirect check could record a page the test never reached (e.g. after a failed login) as the expected page, giving a false PASS; it now stops and asks.

  - **Explorations are rows**: each step with its locator, strategy, score and page, so "which steps need review most often" is a query. `exploration.json` stays the artifact.
  - **Learned page URLs live in the database** (page routes of the Default environment); `pages.json` is imported once and renamed. Batch progress for the server comes from the results, not `batches/*.json`.
  - **Storage references**: uploads, workspaces, evidence and screenshots are named `local:…` / `workspace:…` in rows, never by absolute path; older rows are converted on open.
  - `npm run db -- verify` also checks missing files, orphan evidence files and counters; new `restore <file>` (keeps a copy of what it replaces, refuses a newer or damaged file), `export <folder> [--with-files]` and `import <folder>` (hash-checked NDJSON bundle, loaded into an empty database in one transaction).
