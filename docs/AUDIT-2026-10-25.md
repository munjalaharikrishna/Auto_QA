## 1. Bottom line

1. **The new engine understands test cases better, but almost nothing it understands is executed.** Runs go through the legacy route; the new engine is only a fallback and a gatekeeper. The result is the legacy engine's mistakes plus extra reviews from the new one.
2. **Both engines read test cases blind.** Text is interpreted before the application is looked at, so they cannot know that "Employee ID" is called "Code", or that "login section" is not the Login button.
3. **Wrong PASS is still possible** in several ways, which breaks the BRD's first rule (0% wrong PASS). Measured review reduction is **5%**, against a target of 80%.

## 4. Safety loopholes: wrong PASS is possible (most urgent)

| # | Loophole | Why dangerous | Evidence |
|---|---|---|---|
| S1 | **"X is not displayed" passes whenever X is inside an iframe** (both engines; text, element and catalogue forms) | The check cannot see the iframe, so "not visible" is always true | `generator/plan.ts:361`; `engine/verdict/evaluate.ts:149-235`; vacuity guard too narrow for short names `evaluate.ts:396-401` |
| S2 | **Unvalidated fallback locator.** When locating fails, legacy uses `getByText(target)` with `validated:false` and only a warning; nothing checks `validated` | A negated check then passes without proving anything | `explorer/controller.ts:724-736` |
| S3 | **Project rules can rewrite a sentence into anything.** No validation, versioning, author or scope; import of up to 2000 rules unchecked; screenshot picks silently auto-saved | The 5 Oct wrong PASS ("Appropriate user name … should shown") can still happen | `parser/rules.ts:57`; `parser/index.ts:103`; `server/app.ts:336-341, 371-388`; `db/store.ts:1271-1297`; `server/jobs.ts:289-290` |
| S4 | **The Excel password is replaced.** Any secret-looking Test Data becomes an env reference (`TEST_PASSWORD`); the new engine gets `••••` | TC_LOGIN_003 "wrong password" logs in with the **correct** password, so the negative test proves nothing | `parser/test-data.ts:50-56`; `parser/index.ts:153`; `run-cases.ts:128` |
| S5 | **"PASS (with assumptions)" is still produced, shown and required by tests** (breaks DEC-05) | Assumptions count as PASS | `results/verdict.ts:75, 203-230`; `web/src/pages/JobPage.tsx:506`; `realworld/realworld.test.ts:74-94` |

## 7. Recommended fixes, in order

### Phase A: Stop wrong PASS (first, small)
1. Treat "PASS with assumptions" as NEEDS REVIEW everywhere; update the tests that require it (S5).
2. A negated check may PASS only if the element was located earlier, or every frame was searched; never with an unvalidated locator (S1, S2).
3. Validate project rules before saving (no vacuous or unjudged checks); add history, author and test-case link (S3).
4. Keep Excel secrets per test case in memory; never replace them with a project-wide env value; add TC_LOGIN_003 as a trap (S4).
5. Commit and push everything, push the tag, let CI run.

### Phase B: One engine, not two
6. Shadow mode: every legacy PASS is re-judged by the new engine's verdict engine; disagreement → NEEDS REVIEW (S6, U1).
7. Then the E1.0 switch: one parser, one locator, one verdict system; retire project rules into engine learning with the GV-01 safety rules.

### Phase C: Work on real (iframe) applications
8. iframe support in the new engine: read, locate, observe, wait and check in every frame (E1).
9. Wait for frame navigation and load after each action; re-scan when the page changes during validation (E3).
10. Equivalence rule for identical elements, innermost-container rule for nested holders, row actions (E4, E6).
11. Execute "Logged in" preconditions; identify pages by the content frame's URL (E7, E8).

### Phase D: Better understanding
12. Pass the application's own vocabulary (pages, fields, buttons) into understanding (U2).
13. One vocabulary; tolerate determiners and adjectives; add word forms and missing verbs (U3, U7).
14. Treat setup lines as setup; accept "form or page"; parse "In the X section, do Y" (U4).
15. References to rows, records and other pages (U5).
16. Fix the parser defects in U6.

### Phase E: Measure honestly
17. One frozen baseline from a live run; measure run-time reviews; `engine:gate` fails below 80%.
18. Answer key for the 29 real OrangeHRM cases and a traps folder; run on every change.
19. "Understood" = correct against approved readings of real sentences.

### Phase F: Product and operations
20. PASS/FAIL review card in the UI; connect learning.
21. Clean up created records; one login per worker (`workers: 1` or one account per worker).
22. Move the project and database out of OneDrive; mask test data in the database.
23. Keep Test Data per step; treat expected-only rows as continuation rows; include rule set and app version in the exploration reuse key.

## 8. Expected effect

| | Today | After A–C | After A–E |
|---|---|---|---|
| Wrong PASS risk | Real (6 known loopholes) | Closed | Proven 0 by the answer key |
| 19 OrangeHRM cases as written by testers | 19/19 review | about 8–10 review | **about 2–4** (only genuine test case problems) |
| Review reduction | 5% | about 50% | **80% or more** |

The language engine is not the main bottleneck today. The bigger problems are that **it is not the one running**, **it cannot see iframes**, and **the safety rules do not cover most results**. Fixing those first gives the biggest gain and removes the wrong-PASS risk.
