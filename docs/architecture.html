Auto QA: manual test case to Playwright framework

A deterministic TypeScript platform that turns a written test case into a reviewed, reusable Playwright + POM project, runs it, and reports expected vs actual with evidence. Playwright MCP is only the browser exploration and interaction layer. The platform owns everything else, and nothing in it needs an AI API key.

Design principles

No AI agent: the platform is the MCP clientThe test case is already the plan. Rule-based code follows it step by step and calls the MCP tools itself. D1
Ask, don't guessA vague step, an element with no match, or two equal matches stop the process. The tester picks the element on a screenshot. D6
The platform owns the lifecycleParsing, modeling, locators, codegen, execution, validation, reporting and history live in platform code. MCP only explores and interacts. §5 §26
Deterministic, no AI keyRule-based parsing, scored locator matching and template codegen. A local model can be an optional plug-in later, never a requirement. §27
Generate once, run manyGeneration mode and execution mode are separate. MCP is called again only for a new test, a locator failure, or an explicit re-discovery. §11

Tester stays in controlNothing runs until the tester approves it. The parser never invents steps or assertions the tester didn't write. §12 §19
Secrets never in codeCredentials are injected as process.env at run time and masked in reports. §16

Key decision: MCP without an LLM

Playwright MCP is usually driven by an LLM that reads the page snapshot and decides what to click. Here the platform is the MCP client instead. It calls the tools directly (browser_navigate, browser_snapshot, browser_click, browser_type…) and uses deterministic code to match each step against the returned accessibility snapshot. Locator validation goes through the Playwright library (the Locator Probe), because the check has to use the same engine and locator syntax as the generated test. Both adapters sit behind one BrowserExplorer interface, so either one can be swapped out.

Codegen's role

Playwright Codegen records a person in its own browser. It can't see what MCP does, it hard-codes passwords, and it creates no POM. So it doesn't write scripts here. It is only a "pick locator" backup in review. MCP already reports the Playwright code of every action it runs, and the platform uses that as an extra locator candidate. D4

Core · §4

Test Case Parser

packages/parser

A rule-based pipeline turns free text into the Test Model. It never sends raw text to the browser.

  1. Segment: split the steps on numbering, line breaks and sentence ends. Split the expected result into separate assertion sentences.
  2. Normalise: lower-case, strip filler words ("the", "valid", "successfully"), and keep quoted literals such as 'abc@x.com' intact.
  3. Action lexicon: match the verb. open / go to / navigate → navigate, enter / type / input / fill → fill, click / press / tap / submit → click, select / choose → select, check / tick → check, upload → upload.
  4. Target extraction: the noun phrase after the verb, minus role words ("button", "field", "link"). The role word becomes a roleHint.
  5. Data binding: "valid username" → {{env.TEST_USERNAME}}, a quoted value → literal, "invalid password" → a data-file key.
  6. Assertion patterns: "redirected to X" → url, "X should be displayed" → visible, "message 'Y' shown" → text, "remain on login" → url-not-changed. "Observe/verify" mark a check, and "cannot/does not/rejects" make it a negative check.
  7. Noise and alternatives: "Apply to the Network (or Apply)" gives two candidate names; arrows and filler such as "as applicable" are dropped; browser actions (back, refresh, open URL) are supported.

Any step that matches no rule is marked UNPARSED and shown in review. The parser doesn't guess (§19). The lexicon and synonyms are JSON files, so a team can extend them without code changes.

Importer, Quality Checker, Preconditions & Test Data

src/importer · src/parser
  • Import: Excel/CSV in V1, with a column-mapping screen saved per project (Title, Preconditions, Steps, Test Data, Expected). Jira and TestRail in V2. Steps in one cell are split on numbering.
  • Quality check, before any browser opens: vague steps ("as applicable", "reach X step"), no starting page, and near-duplicate test cases are flagged with a suggestion.
  • Preconditions: "Unauthenticated visitor" → fresh browser; "Logged in" → saved login state; "On Registration page" → a reusable flow (V2) generated once as a Page Object method.
  • Test data: Email=a@b.com pairs from the Test Data column; secrets only from env vars; {{unique.email}} generators (V2) so record-creating tests can run twice.
Core · §5 §6

Exploration Controller + Locator Engine

packages/explorer · packages/locators

Exploration is a guided dry run. The controller performs the steps in order against the real app, because the Dashboard heading only exists after Login is clicked. Before each step it takes a snapshot, finds the target, validates it, then performs the action.

  • Candidate search: walk the snapshot for nodes whose role fits the action (fill → textbox/combobox, click → button/link/menuitem, check → checkbox/radio). Score each node on its accessible name, label, placeholder, data-testid, name/id attributes against the target text, with a synonym table (username ↔ email ↔ user id ↔ login).
  • Nearby text: an element with no name (e.g. a checkbox followed by plain text "checkbox 1") gets that text as a fallback name. done in M1
  • Strategy ladder: for the winning node, build locators in the §6 order: getByTestId → getByRole+name → getByLabel → getByPlaceholder → getByText → CSS → XPath.
  • Validation (Locator Probe): count()===1, visible, enabled/editable, and the action is compatible. The first locator on the ladder that passes wins.
  • Ambiguity rule: if the top two candidates score within a set margin of each other, pick neither. Send both to review as a choice.
  • Page grouping: each element is tagged with the page it was found on (URL path + title), which decides whether it goes in LoginPage or DashboardPage.
  • Fingerprint: store role, name, label, tag, key attributes and parent form. The Recovery Engine uses it later.

Persistence · §7

Locator Repository

locators/*.locators.json

One file per page object, kept in the generated project so it is versioned with the code. The DB mirrors it for querying and history. Each entry holds more than the locator string the document shows, so that recovery and auditing are possible:

{
  "loginButton": {
    "locator": "getByRole('button', { name: 'Login' })",
    "strategy": "role",
    "page": "LoginPage",
    "validatedAt": "2026-09-29T10:14:03Z",
    "fingerprint": { "role": "button", "name": "Login", "tag": "button", "form": "#login-form" },
    "history": []
  }
}

At execution time the generated POM imports these entries. At generation time, a validated entry found here is reused instead of exploring again.

Core · §9 §10 §16

Script & Framework Generator

packages/generator
  • Template-based (Handlebars templates, output formatted by Prettier). For edits to existing files, ts-morph adds a method to a page class without rewriting it.
  • Generates or updates: pages/*Page.ts, tests/*.spec.ts, data/*.data.ts, fixtures/test.fixture.ts, playwright.config.ts, .env.example.
  • Each model step becomes a test.step('S3: Click Login', …), so results map back to the tester's own step numbers.
  • Credentials are always emitted as process.env.TEST_USERNAME!. There is no code path that writes a literal secret.
  • Output is deterministic: the same model always gives byte-identical code, so review diffs are meaningful.
Execution · §11 §18 §22

Execution Manager

packages/executor
  • Spawns npx playwright test --project=<browser> --grep=<testId> in the generated project, with the chosen environment's variables injected into the child process only.
  • A custom Playwright reporter emits onStepBegin/onStepEnd/onTestEnd as JSON lines. The manager relays them to the Event Bus for the live UI.
  • Cross-browser runs use config projects, and parallel runs use workers / fullyParallel. There is no custom browser pool (§22).
  • Auth state: a setup project logs in once and saves storageState. Other tests start logged in (V2).
  • Regression suites (§21) map to a tag or a file list passed to the same command.
Core · §13 §15

Result Validator + Failure Classifier

packages/results

"Actual" is described from captured facts, not generated prose. On any failed step the fixture records the current URL, page title, the first h1/heading, visible role=alert and [aria-invalid] messages, the console errors, and failed network responses. The validator fills the expected/actual template from those facts: "Expected: Dashboard should be displayed. Actual: user remained on /login; alert shown: 'Invalid credentials'."

Every test also gets a built-in health check ("No crash"): no uncaught page errors, no 5xx responses, no error page.

Core · §8

Recovery Engine

packages/recovery · V3
  • Starts only for a Locator Failure, and at most once per step per run.
  • Asks MCP for a snapshot of the current state, scores nodes against the stored fingerprint (role and form must match, the name may differ), and validates the best candidate with the Probe.
  • Policy is set per project: propose (the default: the run is marked "healed, pending approval" and the change waits in review) or auto-apply (the repo is committed straight away).
  • Every change writes a LocatorChange row with old and new locator, score, run ID and screenshots, plus a git commit in the project repo.
Core · §14 §16 §20

Evidence Manager & Reporter

packages/evidence
  • Collects screenshots (per step in generation, on failure in execution), video, trace, console, network errors, the failed locator and assertion, URL, timestamps and duration.
  • Masking: before storage, every string equal to a secret value is replaced with •••• in logs, error messages and reports. Playwright traces record typed values, so traces from tests that type a secret are flagged restricted (download needs permission). Using the auth setup project keeps passwords out of most other traces.
  • Produces a JSON result for the history UI, a standalone HTML report, and a link to npx playwright show-trace.

Things to decide early

Risks & open decisions

Free-text coverage of a rule parserRules will cover the common phrasing and miss unusual sentences. Offer a lightly structured editor (one step per row, with an optional action dropdown), show parse results live as the tester types, and add new lexicon entries whenever a step comes back unparsed.
Exploration performs real actionsThe dry run really clicks Register or Submit, which can create data. Allow exploration only on non-production environments by default, and require explicit confirmation for Production (§17).
Ambiguous targets"Click Save" on a page with three Save buttons. The ambiguity rule sends this to review rather than guessing. The UI should let the tester click the right element in a screenshot to choose it.
Login scopeV1–V4 support username + password only. OTP, MFA and SSO are in the backlog. CAPTCHA must be switched off in the test environment and is never bypassed.
MCP version changesTool inputs change between releases (ref became target). Pin the version and check the tool list at startup (already done in M1).
Unlabeled elements on "any web app"Elements with no name use nearby text first. If that fails, the tester picks the element once, and the locator is saved and reused.
Secrets in tracesPlaywright traces store typed values. Treat traces as restricted, mask the reports, and use the auth setup project so most traces contain no password.
Auto-heal masking real defectsA renamed button can be an intentional change or a bug. Default to propose mode. Never heal assertion targets automatically, only action locators.
Suggested first milestone

Make the §3 login example work end to end against one known app, with Chromium only: parse → explore → validate → generate → approve → run → expected vs actual. Then add one form-heavy test (registration) to stress the parser and the locator scoring before building any V2 features.
